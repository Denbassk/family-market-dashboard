# Разбор структуры проекта — вердикт

Дата: 2026-08-20. Замеры сделаны на рабочих данных (287,4 млн ₴ выручки, 38 точек,
`full_data.json` 6,91 МБ, `index.html` 6 498 строк) и на живой схеме BigQuery.

---

## Коротко

Фундамент выбран правильно, и менять его не надо. Статический HTML + JSON на Cloudflare
для 38 магазинов — это ноль инфраструктуры, ноль расходов на сервер, мгновенный откат
через git и полное отсутствие класса проблем «упала база — упал дашборд». Промежуточная
таблица `_dash_tx26` (один скан вместо трёх десятков) и матрица как единственный источник
категорий — тоже верные решения.

Проблема не в архитектуре, а в **отсутствии контракта**: между Python и JS, между собой
и данными, между «сегодня посчитали так» и «завтра посчитали иначе». Все три аварии,
которые пришлось чинить в этой сессии — удалённая `stock_current`, потерянный фильтр
магазина, опт в среднем чеке — из одного корня: нигде не зафиксировано, что именно
считается правильным, и никто не проверяет, что оно таким осталось.

Ниже — девять пунктов по убыванию отдачи. Первые три дают почти всё.

---

## 1. Нет контракта данных между пайплайном и фронтом

**Факт.** В `full_data.json` 53 ключа. Фронт обращается к ним напрямую (`D.products`,
`D.prod_store`, `D.cat_store` — всего около сорока), почти всегда с молчаливым фолбэком
вида `(D.cross_items||[])`. Если Python перестал собирать ключ, фронт не падает —
он рисует пустую таблицу или, хуже, считает по неполным данным.

**Чем это уже обошлось.** Таблицу `stock_current` удалили из BigQuery, `fetch_data.py`
стал падать, GitHub Action коммитил последний удачный JSON — и на сайт месяц уезжали
остатки месячной давности. Никто не заметил, потому что заметить было нечем.

**Что делать.** Дёшево и радикально:

- `build_data.py` в конце сверяет собранный JSON со списком обязательных ключей
  и падает с внятным сообщением, если чего-то нет. Не коммитим битое.
- В JSON едет `data_meta`: версия схемы, список ключей, дата сборки каждого блока,
  контрольные суммы (выручка, чеки, число точек).
- Фронт при загрузке сверяет `data_meta.schema` со своей ожидаемой версией и, если
  не совпало, показывает баннер «данные собраны другой версией скрипта» вместо тихой лжи.

Полдня работы. Убирает целый класс аварий, включая тот, который уже случился.

## 2. `index.html` перерос себя

**Факт.** 6 498 строк, 321 КБ, четыре инлайн-скрипта, 191 функция, 182 id, 198 CSS-правил.
Четвёртый скрипт (125 КБ, 105 функций) — вкладка «Условия поставщиков» — это фактически
отдельное приложение внутри файла: `formatPctValue` на 292 строки, `exportExcelMarkup`
на 204, `openCompareModal` на 155.

Скрипты не видят переменных друг друга, поэтому форматтеры, экспорт в Excel и работа
с модалками написаны по два раза. Плюс файл правится параллельно из разных сессий —
об этом прямо предупреждает память проекта, и это регулярный источник конфликтов.

**Что НЕ делать.** Не переписывать на React. Простота — главное достоинство этого
проекта, фреймворк её убьёт и потребует сборки там, где сейчас достаточно `git push`.

**Что делать.** Два варианта, оба сохраняют «один файл на выходе»:

- **Минимальный:** вынести «Условия поставщиков» в отдельную страницу `docs/suppliers.html`.
  Это −125 КБ и −105 функций из основного файла за один вечер, вкладка становится ссылкой.
- **Правильный:** держать исходники в `docs/src/*.js` и `docs/src/*.css`, склеивать
  в `index.html` двадцатистрочным питон-скриптом в `build_data.py`. Diff'ы становятся
  читаемыми, параллельные правки перестают конфликтовать, на выходе тот же один файл.

## 3. Доменные правила размазаны по коду

**Факт.** Словарь `NORM` и список `keep` скопированы в `fetch_data.py`, `fetch_page3.py`
и `fetch_stale.py`. При этом в BigQuery уже лежат `store_canon` (49 строк, с полями
`kind`, `opened_from`, `closed_after`) и `store_mapping` (43 строки) — их не использует
никто. Колонки `store_canon` / `store_kind` в `turnover_transactions` заполнены целиком NULL.

**Чем это обошлось.** Оптовая «Полевая магазин» нигде не была помечена как опт, поэтому
средний чек по сети завышался на 13,5 % (166 вместо 147 ₴), причём перекос рос с +7 %
в марте до +19 % в мае–июле. Чинили это правкой, а не данными — потому что данных не было.

**Что делать.** Один модуль `scripts/domain.py`: читает `store_canon` из BigQuery
(с фолбэком на константы, если таблица недоступна), отдаёт `NORM`, `keep`, `WHOLESALE`,
`PROSROK`. Остальные скрипты импортируют его. Заодно заполнить `kind` в `store_canon`
и выкинуть мёртвые колонки из `turnover_transactions`.

## 4. Вес данных: 60 % — три куба позиций

| ключ | вес | доля |
|---|---:|---:|
| `prod_month` | 1 827 КБ | 25,8 % |
| `prod_store` | 1 696 КБ | 24,0 % |
| `in_prod_month` | 726 КБ | 10,3 % |
| `products` | 695 КБ | 9,8 % |
| `heatmap` | 332 КБ | 4,7 % |
| `matrix` | 277 КБ | 3,9 % |
| `sup_store` + `cat_store` | 444 КБ | 6,3 % |
| `store_top_products` | 160 КБ | 2,3 % |

Плюс `stale.json` на 15 МБ отдельным файлом.

Что можно убрать без потери функциональности:

- `store_top_products` полностью перекрыт кубом `prod_store`. Сейчас он остался только
  фолбэком на случай старого JSON и в карточке товара — после следующей пересборки
  фолбэк не нужен, карточку перевести на куб. **−160 КБ.**
- `sup_store` и `cat_store` — это проекции того же куба. Считаются на фронте за 1–2 мс.
  **−444 КБ.**
- `prod_month` и `in_prod_month` хранят по 3 500 товаров × месяцы с полными названиями
  в каждой строке. Перевод на индексы, как в `prod_store`, срежет примерно треть. **≈ −800 КБ.**

Итого около 1,4 МБ из 6,9 без единой потери в функциональности.

## 5. Всё грузится сразу, кроме `stale.json`

Открывая «Обзор», пользователь тянет `matrix` (277 КБ), `heatmap` (332 КБ),
`in_prod_month` (726 КБ) и `dead_items` (160 КБ), хотя ни один из них на «Обзоре»
не нужен. Ленивая загрузка сделана только для «товаров без движения».

**Что делать.** Разделить на `core.json` (Обзор, Позиции, Аналитика) и догружаемые
по вкладкам куски — тем же механизмом, что уже работает для `stale.json`. Первый экран
станет вдвое легче. Это единственная оптимизация скорости, которая тут реально нужна:
расчёты на фронте занимают миллисекунды, всё время уходит на загрузку и парсинг.

## 6. Тесты есть, гейта нет

`tests/check_dashboard.js` прогоняет 36 проверок и ловит ровно те ошибки, которые
случались. Но запускать его надо помнить. `.github/workflows/update.yml` собирает данные
и коммитит их без единой проверки — то есть путь, по которому битые данные уезжают
на прод, до сих пор открыт.

**Что делать.** Две строки в существующий workflow: после сборки данных прогнать
`node tests/check_dashboard.js` и не коммитить, если код возврата не ноль. Плюс второй
workflow на push — синтаксис `index.html` и рендер вкладок. Час работы.

## 7. Смешанные источники внутри одного отчёта

В отчёте «Закупки» магазины считаются по накладным (`torgsoft_incoming_ref_2026`),
а поставщики и категории — по позициям (`_dash_in26`). Разница около 1 %. Это осознанный
компромисс — на уровне накладной мультибрендовый контрагент неразделим, — но в интерфейсе
он никак не подписан, и человек, который сложит два разреза, получит разные числа
и потеряет доверие ко всему отчёту.

**Что делать.** Либо подпись в шапке отчёта, либо (лучше) считать оба разреза от позиций,
а накладные оставить только для сверки в `reconcile.py`.

## 8. Выручка считается по прейскуранту

`price_retail` в `turnover_transactions` — цена до скидки. За Q1 скидки составили
357 604 ₴ (0,37 %), и ровно на столько дашборд завышает выручку. Знает об этом только
`torgsoft_sales_ref`, а он загружен лишь за январь–март.

Исправить сейчас нельзя — нет данных за остальные месяцы. Но подписать в интерфейсе стоит,
и стоит попросить выгрузить эталон продаж за апрель–август: тогда либо появится
поправочный коэффициент, либо выяснится, что скидки выросли и погрешность уже не 0,37 %.

## 9. Мусор, который мешает читать проект

- В BigQuery девять таблиц `assortment_matrix*` / `matrix_*_snapshot` и три бэкапа
  `turnover_monthly*`. Какая из них живая — понятно только по коду.
- В `scripts/` лежат `check_*.py`, `ins_*.py`, `cmp_*.py`, `diag_*.py`, `patch_*.py` —
  одноразовые скрипты отладки. Они в `.gitignore`, но в папке остались и путают.
- `page3_data.json` и `_*_tmp.json` в корне репозитория.

Полчаса уборки. Не срочно, но каждый новый разбор проекта начинается с вопроса
«а это ещё используется?».

## 10. Один год

`YEAR = 2026` захардкожен во всём пайплайне. Сравнений год-к-году нет вообще, хотя
`turnover_transactions` содержит 2025 год (в возвратах данные есть с января 2025).
Для розницы YoY — базовый инструмент: без него сезонность неотличима от роста,
а «падение выручки в магазине» невозможно отличить от «в прошлом году было так же».

Это не недочёт структуры, а незакрытая потребность. Стоит поставить в очередь
сразу после отложенных фич.

## Порядок работ

| фаза | что | зачем | цена |
|---|---|---|---|
| **A** | Контракт данных (п. 1) + гейт в CI (п. 6) | закрывает класс аварий «на сайте старые данные» | 1 день |
| **B** | `domain.py` + `store_canon` (п. 3) | одна правда про магазины, опт и просрочку | 1 день |
| **C** | Разрезать `index.html` (п. 2) | параллельные правки перестают конфликтовать | 1–2 дня |
| **D** | Похудение и ленивая загрузка (п. 4, 5) | первый экран вдвое легче | 1 день |
| **E** | Уборка (п. 7, 9) + подписи (п. 8) | доверие к числам | полдня |
| **F** | YoY (п. 10) | сезонность против роста | 2 дня |

A и B — обязательны, они про надёжность. C — про то, чтобы дальше можно было
работать быстро. Остальное по желанию.

Отложенные фичи (GMROI, ценовые сегменты, корзинная аналитика) после фазы B
делаются заметно проще: куб `prod_store` и единая атрибуция товара уже дают всё,
что для них нужно.
