# Цена BigQuery: сборка 21 ГБ -> 6 ГБ (2026-09-03)

## Как измерять (важно: регион EU!)
`INFORMATION_SCHEMA.JOBS_BY_PROJECT` в `region-us` показывает почти пусто — датасет
`family_market` лежит в **EU**. Правильно:
```sql
SELECT DATE(creation_time) d, COUNT(*) n, ROUND(SUM(total_bytes_billed)/POW(1024,3),1) gb
FROM `region-eu`.INFORMATION_SCHEMA.JOBS_BY_PROJECT
WHERE creation_time >= TIMESTAMP_SUB(CURRENT_TIMESTAMP(), INTERVAL 40 DAY) AND job_type='QUERY'
GROUP BY d ORDER BY d DESC
```
Профилировать колонки бесплатно: `SELECT <col> FROM t` в режиме `dry_run` — вернёт
размер именно этой колонки. Так и нашлось, куда уходят гигабайты.

## Что было (замер 2026-09-03 07:30, сборка целиком)
**61 запрос, 21,13 ГБ.** За 40 дней сервисный аккаунт сжёг 1 610 ГБ, владелец ещё 99 ГБ
при бесплатном лимите 1 ТБ/мес. Причина: `_dash_tx26` — 4,24 млн строк, 943 МБ, из них
**777 МБ (82%) повторяющиеся строки**: product_name 231, tid 175, category 123, store 111,
supplier 77, barcode 60 МБ. И каждый из ~35 агрегатов читал таблицу целиком заново.
Отдельно: тепловая карта читала `turnover_transactions` (917 МБ), а блок sales90 в
fetch_page3 был подставлен ТЕКСТОМ в семь запросов = 5,5 ГБ на сборку.

## Что стало (замер того же дня, полная сборка новым кодом)
**71 запрос, 5,98 ГБ.** Схема: промежуточная `_dash_tx26` (1,70 ГБ, скан TT) -> два прохода
по ней -> дальше все запросы читают маленькие витрины по 20-60 МБ.
- `_dash_a26` (0,74 ГБ на сборку) — агрегат месяц x магазин x штрих-код, ~0,5 млн строк.
  Отсюда ВСЕ суммы и COUNT(DISTINCT barcode/store/category).
- `_dash_r26` (0,62 ГБ) — чеки. COUNT(DISTINCT tid) не складывается, поэтому все разрезы
  одним запросом через GROUPING SETS: (), (mo), (category), (store), (supplier),
  (category,mo), (store,mo), (supplier,mo), (store,dow,hr), (cul), (cul,store).
  Разрез узнаётся по тому, какие колонки не NULL. Тепловая карта берётся отсюда же.
- `_dash_s90` (1,12 ГБ) / `_dash_stk` / `_dash_dead` — витрины fetch_page3.
- В staging добавлены колонки: rev, gp (вместо pr/pp), dow, hr, cul (флаг собственного
  производства), tidn = FARM_FINGERPRINT(tid) для кросс-продаж (32 МБ вместо 175 МБ;
  вероятность коллизии на 1,8 млн чеков ~1e-7, сумм через tidn не считаем).
- `SKIP_STAGING=1` пропускает пересборку ВСЕХ витрин.

## Как проверялась эквивалентность (обязательный ритуал при таких правках)
Старый код прогнан с `SKIP_STAGING=1` по той же исходной таблице -> `ref_main.json`,
новый -> `new_main.json`, сравнение поле в поле по ключам (не по позиции в списке —
порядок строк без ORDER BY не гарантирован!):
- 586 тыс. числовых значений, **все расхождения <= 1 ₴** (порядок сложения float);
- KPI совпал точно, куб prod_store 86 951 ячейка — ключи идентичны;
- page3: разошлись 3 строки, все на границе LIMIT при РАВНОМ значении (593 ₴ и 1613 чеков).
Порядок `D.products` между сборками и так не стабилен (ничьи по выручке) — сравнивать
куб надо по ИМЕНАМ, а не по индексам.

## Кэш запросов бесплатен
Повтор того же запроса по не изменившейся таблице стоит 0. Поэтому «прогнать эталон»
после ночной сборки почти ничего не стоит, а вот пересборка staging инвалидирует кэш
для всех 60 запросов сразу — отсюда и цена.

## Что ещё не сделано (даст минус ~1,5 ГБ на сборку и минус ~8 ГБ/день на стороннем приложении)
1. `turnover_transactions` (2,69 ГБ, 10,2 млн строк) **без партиций**. Её целиком читают
   и staging, и `_dash_s90`, и стороннее приложение (returns_app?) — 2,85 ГБ за прогон,
   2-3 раза в день. Партиционировать по `DATE(transaction_datetime)` + CLUSTER BY store,
   barcode. Риск: если загрузчик Торгсофта делает CREATE OR REPLACE, партиционирование
   слетит (данные не пострадают).
2. Хранение 8,23 ГБ из 10 бесплатных. `turnover_bak_rename_20260818` (2,67 ГБ) — мёртвый
   бэкап; сверено помесячно: строки и выручка совпадают с рабочей таблицей во всех
   20 месяцах, «непарные» 860 тыс. строк — переписанные id при миграции rename.
   Единственная дырка: в январе 2026 в рабочей на 7 строк меньше (37 373 ₴ из 32,4 млн).
   Удаление — командой владельца: `bq rm -f -t family-market-analytics:family_market.turnover_bak_rename_20260818`.

## Правило
Удалять данные (DROP таблицы) — не моя операция даже по прямой просьбе. Проверяю,
что удалять безопасно, и отдаю команду владельцу.
