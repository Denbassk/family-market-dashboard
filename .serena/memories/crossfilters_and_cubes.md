# Кросс-фильтры и кубы (фаза 2, 2026-08-20)

## Что было сломано (замерено, не гипотеза)
`workProducts()`: `base = (S.store.length===1) ? store_top_products : D.products;`
- один магазин -> ТОП-30 позиций на точку, покрытие 26,5% выручки
  (Іскринський 19В: 2 914 609 ₴ вместо 11 265 143 ₴);
- ДВА и более магазинов -> фильтр магазина ИГНОРИРОВАЛСЯ: 278 884 573 ₴ (вся сеть)
  вместо 18 515 491 ₴. KPI на «Обзоре» показывал это с пометкой «≈ оценка»;
- `storeAgg()`: ветка `sup_store` шла первой и теряла фильтр категории
  (категория+поставщик давало ровно то же, что один поставщик).

## Правило аддитивности (записано комментарием над workProducts)
- МАГАЗИНЫ: выручка/прибыль/единицы/**ЧЕКИ** складываются (чек принадлежит одному магазину),
  **SKU нет** — один товар продаётся в нескольких точках.
- КАТЕГОРИИ и ПОСТАВЩИКИ: выручка/прибыль/единицы/**SKU** складываются (товар в одной категории
  и у одного поставщика), **ЧЕКИ нет** — один чек содержит несколько категорий.
`kpiNow()` строит точный ответ через `roll(rows, keepReceipts, keepSkus)` для ЛЮБОГО мультивыбора
одного измерения (раньше точный путь работал только при выборе РОВНО одного значения).

## Куб `prod_store` (fetch_data.py)
Строка = `[индекс в D.products, индекс в D.stores, выручка, прибыль, кол-во]` — имена не дублируются.
86 106 строк, покрытие 100% (все 4 364 названия влезают в LIMIT 4500), +1,65 МБ к JSON
(6,8 -> 8,4 МБ; gzip 1,71 МБ — Cloudflare отдаёт сжатым). Агрегация на фронте 1,5–2 мс.
Помесячного куба по точкам НЕТ намеренно: product×store×month = 398 721 строка (~10 МБ) — слишком тяжело.
`prod_store_meta` держит rows / lost_rows / lost_revenue / covered_pct.

## Деградация, пока данные не пересобраны
`byStoreRows()` в workProducts: есть куб -> точно; нет куба -> ОБЪЕДИНЕНИЕ `store_top_products`
по выбранным точкам (~26% выручки, суммируются дубли между магазинами), `exact=false`.
Пустой список тут был бы хуже неполного. Подпись в «Позициях» тогда:
«≈ оценка: ТОП-30 на точку, нажмите „Обновить данные"», иначе «≈ оценка (месяц × магазин)».

## Единственный неточный срез при полных данных
МЕСЯЦ + МАГАЗИН одновременно: месячная выручка позиции раскладывается по точкам пропорционально
их годовой доле. Флаг `WP_EXACT=false`, в заголовке графика магазинов — `STORE_AGG_EXACT`.
Замер: 1 462 919 против 1 467 227 по BigQuery — 0,3%. KPI при этом ТОЧНЫЙ (из `store_month`).
ВАЖНО: `WP_EXACT` выставляется ВНУТРИ `workProducts()` — читать флаг только ПОСЛЕ вызова
(на этом уже один раз попался ложный FAIL в тестах).

## Кэш
`WP_CACHE` по ключу из всех полей фильтра, `wpReset()` вызывается в `load()`.
Без него `catAgg()` звал `workProducts()` трижды (в т.ч. заново на каждую категорию — O(n²)).

## Единая категория/поставщик на НАЗВАНИЕ товара (staging `_dash_tx26`)
Корневая причина, почему срезы не бились между вкладками: у товара бывает два штрих-кода
(штучный и упаковка), в матрице лежит только один -> часть выручки одной позиции уезжала
в «(нет в матрице)», а `products` (ANY_VALUE по названию) расходился с `by_category` (по строкам).
Замер: 50 названий из 4 364 имели >1 категории/поставщика — 6,67 млн ₴ (2,3% выручки).
Решение в CREATE TABLE: вес = выручка ТОЛЬКО матричных штрих-кодов, `ANY_VALUE(x HAVING MAX w)`.
Эффект: выручка и число строк не изменились, `offmatrix_rev` 18,62 -> 16,58 млн (−2,04 млн
вернулось реальным поставщикам: Хладік, Грин Дей, Дісна, Авангард…). Все переезды только
из «(нет в матрице)» в реальное имя, обратных нет. Наследуется и в `fetch_page3.py`
(он читает тот же `_dash_tx26`), так что неликвиды/дефицит тоже стали точнее.

## Автотесты
`tests/check_dashboard.js` — jsdom без браузера, `node tests/check_dashboard.js` из корня репо
(нужен `npm i jsdom`). 32 проверки: рендер 9 вкладок × 8 комбинаций фильтров (72 прогона),
кросс-фильтры против by_store/monthly и против BigQuery, аддитивность куба возвратов, DOM «Обзора».
В шапке печатает, что есть в данном full_data.json (куб / возвраты / дата сборки).
Три состояния: OK / FAIL / «пропущено». Проверки, которым нужен куб или возвраты, при старом
JSON идут как ПРОПУЩЕННЫЕ, а не проваленные — иначе «данные не пересобраны» читается как «сломано».
Коды возврата: 0 — всё зелено; 1 — реальные провалы или рантайм-ошибки; 3 — провалов нет,
но данные устарели и проверено не всё.
Контрольные числа из BigQuery: `python tests/truth.py` -> `tests/truth.json` (в .gitignore,
файл машинозависимый). Без него BQ-проверки пропускаются. Тест берёт поставщика, который лежит
в НЕСКОЛЬКИХ категориях, иначе проверка «категория+поставщик != только поставщик» вырождается.
