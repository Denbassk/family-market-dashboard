# Имена магазинов: единый источник `scripts/domain.py` (2026-08-21)

## Что было сломано
`fetch_stale.py` имел СВОЙ словарь нормализации на 7 ключей вместо общего NORM на 42.
Из-за этого 12 из 38 точек в `docs/stale.json` писались иначе, чем во всём дашборде
(«Іскрінський 19» / «Іскринський 19В», «Бучми Джерело» / «Бучми 32Б1»,
«Полевая-Магазин» / «Полевая магазин», «Пр-т Ювілейний 67» / «Ювілейний 67» …),
и «Товары без движения» нельзя было сопоставить ни с одним другим экраном.
`mem:data_pipeline` утверждала, что имена в stock_matrix совпадают с ключами NORM —
для fetch_stale.py это было НЕВЕРНО.

## ГЛАВНОЕ: канона имён в BigQuery НЕТ (проверено на живой схеме 2026-08-21)
Собственник предлагал взять «правильные адреса» из эталона приходов. Не выйдет:
| таблица | что там на самом деле |
|---|---|
| `torgsoft_incoming_ref_2026` | 42 имени, из них **38 — СЫРЫЕ ключи NORM**, не канон; плюс Полевая-Просрок / Полевая-Склад / Производство / Склад |
| `store_canon` (49 строк) | совпадает с NORM только в 28 из 42; в 14 случаях в колонку `store_canon` продублировано СЫРОЕ имя; «Полевая 83» отнесена к «Полевая-Склад» (в дашборде это «Полевая магазин»). Колонка `kind` заполнена: retail/opt/sklad/prosrok |
| `store_mapping` (43 строки) | 27 из 42, та же болезнь |
Ни одна таблица не знает, что «Іскрінський 19» = «Іскринський 19В». Эти переименования
заведены руками и живут только в коде. Поэтому `domain.py` — КОНСТАНТЫ.
Когда `store_canon` приведут в порядок (записать туда настоящие канонические имена),
`domain.py` сможет читать её с фолбэком — это фаза B из `mem:architecture_review`.

## Что сделано
Новый `scripts/domain.py`: `NORM` (42 сырых -> 38 канонических), `WHOLESALE`,
`SERVICE_STORES`, `STORES`, `canon()`, `sql_case()`, `sql_case_full()`, `sql_keep()`.
- `sql_case()`/`sql_keep()` дают строку, ПОБАЙТНО совпадающую с прежним инлайн-кодом
  (проверено сравнением: cases 2 173 симв., keep 770 симв., cs_wo 2 467 симв.).
- `sql_case_full()` — с `ELSE TRIM(col)`: незнакомые имена остаются как есть.
  Нужен для снимка остатков, где служебный «Полевая-Склад» (5,3 млн ₴ запаса)
  ДОЛЖЕН остаться в отчёте и прятаться ползунком, а не выпадать из выборки.
`fetch_data.py`, `fetch_page3.py`, `fetch_stale.py` теперь импортируют domain.
Импорт устойчив к cwd: `sys.path.insert(0, os.path.dirname(os.path.abspath(__file__)))`.
build_data.py запускает скрипты подпроцессами — этого достаточно.

## Побочно исправлено в fetch_stale.py (сказать собственнику)
Поставщик выбирался НЕДЕТЕРМИНИРОВАННО: `ROW_NUMBER() OVER (PARTITION BY barcode
ORDER BY DATE(doc_date) DESC)` без тай-брейка. При нескольких приходах товара в один день
BigQuery возвращал произвольную строку — два прогона подряд давали разных поставщиков
у 267 строк из 44 234 (и вместе с ними прыгал флаг «технический», 69 строк).
Фильтр «Поставщик» на карточке менялся после каждой пересборки. Добавлен тай-брейк
`, {I_SUP}`; два независимых прогона теперь дают побитово одинаковый результат.
ТА ЖЕ БОЛЕЗНЬ, вероятно, есть в `ANY_VALUE(... HAVING MAX w)` в staging `_dash_tx26`
и в порядке `D.products` (порядок между сборками меняется на равных выручках, из-за чего
индексы в кубе `prod_store` съезжают — на цифры не влияет, но ломает поиндексное сравнение).
